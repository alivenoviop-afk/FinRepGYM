# Правила семантики ошибок и решений (v1) — на утверждение командой

> Это страница правил, о которой договорились 19.11. Она же — основа «Записки о дизайне»
> и источник истинных значений для генератора и эталона. Менять её после дня 2 можно
> только вместе с тестами.

## Общие принципы

1. **Эталон описывает реальное расхождение**, а не случайную подозрительную строку.
2. **Нельзя требовать недоступный факт:** каждое доказательство из `truth.json` обязано
   быть разрешимо в открытых файлах (`ledger.csv`, `invoices.jsonl`, `payments.jsonl`,
   `fx.csv`, `policy.json`, `manifest.json`).
3. **Сложность = анализ доказательств,** а не противоречивость данных. Противоречивые
   или неразрешимые данные — это брак, а не «трудный уровень».
4. **Вариативность обязательна:** имена, ID, порядок строк, суммы, валюты, часовые пояса
   и сочетания ошибок меняются от эпизода к эпизоду.
5. **Все суммы — целые минимальные единицы;** курсы — десятичные строки; время — ISO-8601
   со смещением; отсутствующие ссылки — явный `null`.

## Решение 1. Дубль счёта — `duplicate_entry` ✅ (реализовано)

- **Признак:** две записи, идентичные по **всем полям кроме `row_id`** (дата-время, счёт,
  дебет, кредит, валюта, контрагент, счёт-фактура, платёж).
- **Инъекция:** копируется кредитная строка выручки. В чистых книгах равенство
  `Σдебет − Σкредит = 0`; после инъекции оно равно `−сумма_строки`.
- **affected_ids:** **обе строки пары** (сортировка — канон). Причина: после
  перестановки и переименования из данных невозможно определить, какая из двух
  идентичных строк была «копией», — эталон обязан указывать на пару, иначе ответ
  не переносится на новые ID (это поймала проверка на воспроизводимость, 19.11).
- **expected_amount_minor:** сумма скопированной строки; допуск `0`.
- **Доказательства (2 допустимых полных набора):**
  - `{ledger:<дубль>, ledger:<оригинал>, invoice:<счёт-фактура>}`
  - `{ledger:<дубль>, ledger:<оригинал>}`
- **Что НЕ является дублем (обязательные отвлекающие):** две разные счета на одну сумму
  (разные `invoice_id`); две части разбитого платежа (разные `payment_id`); одинаковые
  строки по разным счетам.

## Решение 2. Границы отчётного периода — `policy.json` ✅ (реализовано)

- Границы **включительно:** `period_start 00:00:00` … `period_end 23:59:59`
  в часовом поясе эпизода.
- Все метки времени эпизода имеют одно и то же смещение → лексикографическое сравнение
  строк эквивалентно сравнению моментов времени (зафиксировано и проверяется тестом).
- Проверка «в периоде» для документа и для строки леджера выполняется **одинаково**.

## Решение 3. Частичное/пропущенное распределение платежа — `partial_allocation` ✅ (реализовано 19.11)

- **Смысл:** платёж по документу существует в полной сумме, но в журнале
  распределена только его часть.
- **Инъекция:** документ платежа не меняется; **обе** строки журнала (дебет кассы
  и кредит дебеторки) уменьшаются на недостающую сумму → книги остаются
  сбалансированными, а дебиторка внутри периода завышена ровно на эту сумму.
- **Декларируемое расхождение:** `ар_баланс_в_периоде − (выставлено − оплачено_по_документам)`
  = сумме недостающей части; независимо: сумма платежей по счёту (документы)
  минус погашения дебеторки по этому счёту = та же сумма.
- **affected_ids:** `[payment_id, обе строки журнала]`.
- **Доказательства (2 допустимых полных набора):**
  - `{payment:<id>, ledger:<строка дебеторки>, invoice:<счёт-фактура>}`
  - `{payment:<id>, ledger:<строка кассы>, ledger:<строка дебеторки>}`
- **Не путать с (законно):** неоплаченный счёт; разбитый платёж, где сумма частей
  равна счёту; возврат; платёж, проведённый после границы периода.
- **Допуск:** `0`.
- **Сверка обязана находить:** тест `test_reconciliation_finds_all_three_implemented_types`
  (TP=3, FP=0, FN=0).

## Решение 4. Курс или дата конвертации — `fx_rate` ✅ (реализовано 19.11)

**Модель валют (важно):**
- Документы живут в **своей валюте** (`currencies`: USD, EUR, KZT — объявлено в манифесте с разрядностями).
- Платёж **в валюте счёта** постится в этой же валюте (пара одинакова, баланс точен).
- Платёж **в другой валюте** постится целиком в **базовой валюте**: обе строки используют один
  сконвертированный целый результат → `Σдебет = Σкредит` и сверка дебиторки сходятся **без
  округлительного дрейфа** (цепочки конвертаций исключены по построению).
- Конвертация всегда по курсу `policy.fx_rate_date` (= `period_end`) из `fx.csv`,
  десятичные строки, округление half-up до разрядности целевой валюты.
- Разные валюты **нельзя сравнивать без конвертации** — это правило прямо прописано в `policy.json`.

- **Признак ошибки:** конвертированная строка кросс-валютного платежа посчитана не по policy-курсу.
- **Декларируемое расхождение:** `Σдебет − Σкредит` (в базе) и AR-расхождение сдвигаются на
  величину `неверный_курс − верный_курс`, пересчитанную из открытых `fx.csv` и документов.
- **affected_ids:** `[payment_id, обе строки постинга]`.
- **Доказательства (2 допустимых полных набора):**
  - `{payment:<id>, ledger:<AR-строка>, fx:<policy-дата:источник:база>, policy:fx_rate_date}`
  - `{payment:<id>, ledger:<строка кассы>, ledger:<AR-строка>, policy:fx_rate_date}`
- **Допуск:** **строго 0** (решение команды, 19.11).
- **Сверка обязана находить:** тест `test_reconciliation_finds_all_four_implemented_types`
  (TP=4, FP=0, FN=0) и свип `check.py` по 13 seed'ам.

## Обязательные сценарии взаимодействия (2 штуки)

| ID | Сценарие | Сочетание типов | Почему сложнее |
|---|---|---|---|
| **S1** | Частичный платёж **в другой валюте** на границе периода | `partial_allocation` + `fx_rate` (+ `period_cutoff`) | расхождение нужно считать после конвертации и внутри периода одновременно |
| **S2** | Дубль строки **и** переезд строк платежа за границу периода | `duplicate_entry` + `period_cutoff` | два независимых расхождения в одном эпизоде; аддитивно должны сходиться с `truth.json` |

Каждая ошибка в сценарии — отдельная запись в `truth.json` со своей причинной записью в
`provenance.json`; суммарное расхождение обязано совпасть с независимым пересчётом по
открытым файлам (это проверяет отдельный тест).

## Обязательные чистые случаи и отвлекающие

- разбитые платежи (сумма частей = сумме счёта);
- повторяющиеся одинаковые суммы у разных счетов;
- возвраты;
- неоплаченные счета;
- платежи, легально проведённые после границы периода;
- счета, выпущенные в последний день периода.

Сверка (`ReconciliationPolicy`) обязана давать **0 ложных срабатываний** на чистых
эпизодах — это закреплено тестом.

## Решение 5. Возвраты — генерируем как законную операцию ✅ (реализовано 19.11)

- **Статус:** возвраты прямо названы в спеке среди обязательных отвлекающих случаев;
  первый оплаченный счёт получает возврат **гарантированно**, остальные — по вероятности.
- **Представление:** пара строк «дебет выручки / кредит кассы» → баланс книг
  сохраняется, **дебиторка не затрагивается**, в `truth.json` возврата нет.
- **Поведение политики:** правильный ответ на возврат — **ничего не находить**;
  пометка возврата = ложноположительная находка и штраф.
- **Совместимость со сверкой:** возврат не влияет на правило «платежи = погашения
  дебеторки» (кассовая операция), поэтому сверка не меняется.
- **Тесты:** `test_returns_are_legal_and_never_flagged` (возвраты есть, не в truth,
  баланс цел) и `test_reconciliation_stays_silent_on_clean_books` (0 ложных
  срабатываний на чистых эпизодах с возвратами).

## Решение 6. Оси конфигурации для закрытых проверок

Спека: закрытая проверка = скрытые seed + **новые сочетания параметров** + безвредные
преобразования. Значит, жюри **собирает эпизоды из наших осей** — оси и надёжность
любого сочетания важнее количества сданных файлов.

| Ось | Значения | Статус |
|---|---|---|
| `seed` | любое целое | ✅ |
| `clean` | да/нет (ноль ошибок гарантирован) | ✅ |
| `issue_types` | подмножество 4 типов | ✅ 4 из 4 |
| `n_issues` | 0–12 | ✅ 0–4 (потолок 12 достигается конфигом) |
| размер | 200–2000 строк, 20–200 документов | ✅ |
| `distractors` | вкл/выкл отвлекающих | ✅ |
| период / часовой пояс | разные границы и смещения | ✅ включая смещения в минутах (+09:30) |
| валюты и курсы | одна / несколько | ✅ USD/EUR/KZT, кросс-платежи, policy-курс |
| возвраты, плотность платежей | густо/редко | ✅ (возвраты, разбитые платежи) |
| безвредные преобразования | перестановка строк, смена id | ✅ `transforms.py`, 10 пар в `check.py` |
| безвредные преобразования | перестановка строк, смена id | ⬜ парные проверки |

**Раскладка 5/5/5/5 утверждена (19.11):** закрытый набор из 20 эпизодов —
5 чистых + 5 одиночных + 5 с двумя типами + 5 со взаимодействием; в открытом
наборе жюри это обеспечивается осями `clean`, `issue_types`, `n_issues`.

**Предложение по открытым эпизодам (сдаём 10+10, минимум по спеке):**
train = 2 чистых + 4 одиночных (все 4 типа) + 2 с двумя типами + 2 взаимодействия;
dev = 1 чистый + 4 одиночных + 3 с двумя типами + 2 взаимодействия;
размеры и seed разбросаны от минимального до максимального. Расширять до 20+20 —
только если останется время после типов 3–4 и пермутаций (количество не оценивается,
оценивается покрытие и непротиворечивость).
