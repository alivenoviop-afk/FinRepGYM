# Правила семантики ошибок и решений (v1) — на утверждение командой

> Это страница правил, о которой договорились 19.11. Она же — основа «Записки о дизайне»
> и источник истинных значений для генератора и эталона. Менять её после дня 2 можно
> только вместе с тестами.

## Общие принципы

1. **Эталон описывает реальное расхождение**, а не случайную подозрительную строку.
2. **Нельзя требовать недоступный факт:** каждое доказательство из `truth.json` обязано
   быть разрешимо в открытых файлах (`ledger.csv`, `invoices.jsonl`, `payments.jsonl`,
   `fx.csv`, `policy.json`, `manifest.json`).
3. **Сложность = анализ доказательств,** а не противоречивость данных. Противоречивые
   или неразрешимые данные — это брак, а не «трудный уровень».
4. **Вариативность обязательна:** имена, ID, порядок строк, суммы, валюты, часовые пояса
   и сочетания ошибок меняются от эпизода к эпизоду.
5. **Все суммы — целые минимальные единицы;** курсы — десятичные строки; время — ISO-8601
   со смещением; отсутствующие ссылки — явный `null`.

## Решение 1. Дубль счёта — `duplicate_entry` ✅ (реализовано)

- **Признак:** две записи, идентичные по **всем полям кроме `row_id`** (дата-время, счёт,
  дебет, кредит, валюта, контрагент, счёт-фактура, платёж).
- **Инъекция:** копируется кредитная строка выручки. В чистых книгах равенство
  `Σдебет − Σкредит = 0`; после инъекции оно равно `−сумма_строки`.
- **affected_ids:** `[дублирующая строка]` (канон — сортировка, поэтому порядок не важен).
- **expected_amount_minor:** сумма скопированной строки; допуск `0`.
- **Доказательства (2 допустимых полных набора):**
  - `{ledger:<дубль>, ledger:<оригинал>, invoice:<счёт-фактура>}`
  - `{ledger:<дубль>, ledger:<оригинал>}`
- **Что НЕ является дублем (обязательные отвлекающие):** две разные счета на одну сумму
  (разные `invoice_id`); две части разбитого платежа (разные `payment_id`); одинаковые
  строки по разным счетам.

## Решение 2. Границы отчётного периода — `policy.json` ✅ (реализовано)

- Границы **включительно:** `period_start 00:00:00` … `period_end 23:59:59`
  в часовом поясе эпизода.
- Все метки времени эпизода имеют одно и то же смещение → лексикографическое сравнение
  строк эквивалентно сравнению моментов времени (зафиксировано и проверяется тестом).
- Проверка «в периоде» для документа и для строки леджера выполняется **одинаково**.

## Решение 3. Частичное/пропущенное распределение платежа — `partial_allocation` ⬜ (день 2)

- **Смысл:** платёж по документу существует, но отнесён в леджере неполно либо на другой
  счёт-фактуру.
- **Декларируемое расхождение:** сумма платежей по счёту-фактуре (документы) минус сумма
  кредитов `1200_accounts_receivable` по этому счёту = недостающая сумма.
- **affected_ids:** `[payment_id, строки леджера платежа]`.
- **Доказательства:** `{payment:<id>, ledger:<строка>, invoice:<счёт-фактура>}`.
- **Не путать с (законно):** неоплаченный счёт; разбитый платёж, где сумма частей равна
  счёту; возврат; платёж, отнесённый по счёту верно, но позже.
- **Допуск:** `0`.

## Решение 4. Курс или дата конвертации — `fx_rate` ⬜ (день 2)

- **Правило:** курс берётся **на `period_end`** (`policy.fx_rate_date = "period_end"`)
  из `fx.csv`, десятичными строками.
- **Декларируемое расхождение:** применён курс другой даты → сумма в базовой валюте
  отличается от суммы, пересчитанной по правильному курсу.
- **Мультивалюта:** `ledger.currency` — валюта транзакции; сравнение разных валют
  **запрещено без конвертации** в `base_currency` по `policy.json`.
- **affected_ids:** `[строка леджера, fx-запись правильной даты]` (fx-записи имеют
  составной id `дата:источник:назначение`).
- **Доказательства:** `{ledger:<строка>, fx:<дата:src:tgt>, policy:fx_rate_date}`.
- **Допуск:** `1` минимальная единица (допускается на случай half-up округления) —
  **открытый вопрос №1.**

## Обязательные сценарии взаимодействия (2 штуки)

| ID | Сценарие | Сочетание типов | Почему сложнее |
|---|---|---|---|
| **S1** | Частичный платёж **в другой валюте** на границе периода | `partial_allocation` + `fx_rate` (+ `period_cutoff`) | расхождение нужно считать после конвертации и внутри периода одновременно |
| **S2** | Дубль строки **и** переезд строк платежа за границу периода | `duplicate_entry` + `period_cutoff` | два независимых расхождения в одном эпизоде; аддитивно должны сходиться с `truth.json` |

Каждая ошибка в сценарии — отдельная запись в `truth.json` со своей причинной записью в
`provenance.json`; суммарное расхождение обязано совпасть с независимым пересчётом по
открытым файлам (это проверяет отдельный тест).

## Обязательные чистые случаи и отвлекающие

- разбитые платежи (сумма частей = сумме счёта);
- повторяющиеся одинаковые суммы у разных счетов;
- возвраты;
- неоплаченные счета;
- платежи, легально проведённые после границы периода;
- счета, выпущенные в последний день периода.

Сверка (`ReconciliationPolicy`) обязана давать **0 ложных срабатываний** на чистых
эпизодах — это закреплено тестом.
